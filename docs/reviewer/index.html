Data structures & algorithms primer

n = number of records · k = length of a text or number of results · b = number of hash buckets. All of these live in assets/js/dsa/.

arrayAppend writes at index length: O(1). arrayInsertAt shifts the later items right: O(n). arrayRemoveAt shifts left: O(n). Reading a[i]: O(1).

Linear search — O(n)

Starter1stStream2ndPowermatchProUltimate

Check the items one by one until one matches. Works on any array (sorted or not). Best case O(1), worst O(n).

Binary search — O(log n)

48714872487348744875middle48764877

Needs a sorted array. Look at the middle; if the target is bigger keep the right half, else the left half. Each step halves the range: 17 records need at most 5 steps, 100,000 need about 17.

Lower bound + sorted insert (“put”) — O(n)

487248744875goes here4878→ moves4881→ moves

A binary search finds the first position whose key is ≥ the new key (O(log n)); then the later records shift one slot right (O(n)). The array stays sorted, so binary search keeps working.

Insertion sort — best O(n), worst O(n²), stable

Take the next item and slide the bigger items to the right until its place is found. Very fast when the list is already almost sorted — our tables usually are — so it is our default.

Selection sort — always O(n²), not stable

For each position, scan the rest for the item that belongs there and swap it in. Always n(n−1)/2 comparisons, but at most n−1 swaps — the fewest moves.

Bubble sort — best O(n), worst O(n²), stable

Walk the list swapping neighbours that are in the wrong order; after each pass the biggest item has “bubbled” to the end. Stops early when a pass makes no swap.

Naive string matching — O(n·m)

Used by every search box: try every starting position of the text and compare letter by letter (“jua” finds “Juan Dela Cruz”), ignoring capital letters.

Stack — LIFO, push / pop / peek O(1)

Approve AReject BConfirm Ptop

Record { items, top }. Undo pushes every admin action and pops the newest (last in, first out). Also the Back button and open dialogs.

Queue — FIFO, circular buffer, enqueue / dequeue O(1)

PAY-2[0] frontPAY-3[1]PAY-4[2]·[3] rear

Record { items, front, count, capacity }; the rear is (front + count) % capacity, so nothing is shifted. First come, first served: review queue, payment validation, staff requests, support tickets, oldest bill first.

Hash table — separate chaining, O(1) average

[0]empty
[1]key A → value
[2]key B → value → key C → value
[3]empty

The key is turned into a bucket number with the djb2 hash (hash × 33 + character, then the remainder). Keys that share a bucket (a collision) form a short chain. Grows when there are more than 0.75 keys per bucket.

Why procedural?

Every structure is a plain record plus functions that receive it (e.g. stackPush(stack, item)) instead of objects with methods. This follows the project rule and makes each step of the algorithm visible.

Likely panel questions

Why linear search for the plans and not binary search?

There are only 5 plans; binary search would save at most 2 comparisons. The recommender also needs the first plan whose speed is at least a value — a single pass in speed order does exactly that.

Why is the applications array always sorted without sorting it?

Reference numbers come from a counter that only goes up (E3-2026-004886, …004887). A new application always has the largest number, so appending it at the end keeps the order — O(1), no sort needed.

What is the worst case of your binary search?

⌈log₂(n+1)⌉ comparisons: 5 for our 17 applications, 14 for 10,000. A linear search would need up to n.

Why selection sort for the plan cards?

It makes the fewest swaps (at most n−1) and its cost is predictable: always n(n−1)/2 = 10 comparisons for 5 plans — the page prints that number under the cards.

How do you validate without regular expressions?

Each rule scans the characters with a loop — e.g. the e-mail must have exactly one “@”, allowed characters only and a dot after it; the mobile number is reduced to its digits and must be 11 digits starting with 09.

Why hide part of the name on the tracker?

Anyone who knows or guesses a reference number can open the tracker, so it shows “Ana R.” instead of the full name, and never the address or ID.

Recommender (recommendPlan):

  1. Find the chosen device range and activity with a linear search (findDeviceRange, findActivity).
  2. Compute the speed needed: devices × Mbps per device (e.g. 10 × 10 = 100 Mbps).
  3. Put the plans in speed order with insertion sort. They are stored in speed order already, so this is its best case: n−1 = 4 comparisons, 0 moves.
  4. Linear search from the slowest plan: stop at the first plan whose speed ≥ the needed speed — that is also the cheapest one that is fast enough.
  5. If no plan is fast enough, recommend the fastest plan (Ultimate).

Sorting the cards (selectionSort): copy the array; for each position scan the rest for the plan that belongs there (e.g. the most expensive) and swap it in; count comparisons and swaps and print them under the cards.

Choosing: the button opens #/apply/<id>; the Apply screen checks the id with findPlan (linear search) and pre-selects that plan in step 1.

6Justification

Why did you choose that data structure or algorithm? Why is it appropriate?

  • Array of records: plans are a small, fixed list that is shown in order — an array is the simplest structure and is read in O(1) by index.
  • Linear search: with 5 items it is as fast as anything else, needs no sorted key, and naturally answers “the first plan that is fast enough”. Binary search would need the plans sorted by the searched field and saves at most 2 comparisons.
  • Insertion sort for the speed order: the plans are already in that order, which is insertion sort’s best case (linear time).
  • Selection sort for the cards: at most n−1 swaps and a fixed, easy-to-explain number of comparisons, which we display to the user. For 5 items O(n²) is only 10 comparisons.

assets/js/dsa/sort.js · lines 109–135

109/**
110 * selectionSort — for each position, scans the unsorted part for the item
111 * that belongs there (the smallest, or largest when descending) and swaps it in.
112 * Always makes n(n−1)/2 comparisons but at most n−1 swaps.
113 * Time: O(n²) in every case · Space: O(1) extra (plus the copy) · Stable: no
114 */
115function selectionSort(records, field, order) {
116  const list = arrayCopy(records);                  // sort a copy, so the table keeps its own order
117  const direction = order === 'desc' ? -1 : 1;
118  let comparisons = 0;
119  let swaps = 0;
120  for (let i = 0; i < list.length - 1; i++) {       // 1. fill position i (0, 1, 2 …) with the right item
121    let best = i;
122    for (let j = i + 1; j < list.length; j++) {     // 2. scan everything after it
123      comparisons++;
124      if (compareForOrder(list[j][field], list[best][field], direction) < 0) {
125        best = j;                                   //    remember the item that should come first
126      }
127    }
128    if (best !== i) {                               // 3. swap that item into position i
129      arraySwap(list, i, best);
130      swaps++;
131    }
132  }
133  recordRun('Selection sort', comparisons, swaps);
134  return list;
135}
  1. arrayCopy makes a copy (our replacement for slice) so the original order stays; direction is −1 for “high to low”.
  2. The outer loop fills position i; the inner loop scans the rest and remembers in best the item that should come first.
  3. compareForOrder compares two values in the chosen direction; empty values always go last.
  4. arraySwap exchanges two slots (no built-in helper). Only one swap per position → at most n−1 swaps.
  5. recordRun saves the comparison and swap counts, which the page prints under the cards.

6Justification

Why did you choose that data structure or algorithm? Why is it appropriate?

  • Append to a sorted array: reference numbers only grow, so appending is O(1) and keeps the array sorted — this is what makes the tracker’s binary search possible without ever sorting.
  • Linear search for duplicates: the rule depends on the status (only open applications count), on two fields (e-mail or mobile) and on text normalisation; a single pass handles all of that. A hash table would need an index per field and updates on every status change — not worth it for our size.
  • Binary search for the barangay: the list is fixed and sorted by name, so the look-up is O(log B).
  • Hand-written character checks: required by the project rules (no regular expressions) and they give a precise message for each kind of mistake.
  • The wizard reuses the backend validator, so the screen and the saved data follow exactly the same rules.

76/**
77 * binarySearch — index of the record whose `field` equals `value`, or -1.
78 * The records MUST be sorted by `field` in ascending order. Each step looks at
79 * the middle record and discards the half that cannot contain the value.
80 * Time O(log n) — about 17 steps for 100,000 records · Space O(1)
81 */
82function binarySearch(sortedRecords, field, value) {
83  let low = 0;                                      // 1. start with the whole table as the range
84  let high = sortedRecords.length - 1;
85  let comparisons = 0;
86  while (low <= high) {                             // 2. repeat while the range still has records
87    const middle = Math.floor((low + high) / 2);    // 3. look at the middle record
88    const middleValue = sortedRecords[middle][field];
89    comparisons++;
90    if (middleValue === value) {                    // 4. found it
91      recordRun('Binary search', comparisons, 0);
92      return middle;
93    }
94    if (middleValue < value) {
95      low = middle + 1;   // the value can only be in the right half
96    } else {
97      high = middle - 1;  // the value can only be in the left half
98    }
99  }
100  recordRun('Binary search', comparisons, 0);
101  return -1;
102}
  1. low and high mark the part of the table that can still contain the target.
  2. The loop runs while that part is not empty.
  3. Math.floor((low + high) / 2) is the middle position; its key is compared with the target.
  4. Equal → found. Smaller → the target can only be to the right (low = middle + 1). Bigger → to the left (high = middle − 1).
  5. If the loop ends, the key is not in the table and −1 is returned. The comparisons are recorded either way.

137/**
138 * insertionSort — grows a sorted part at the front: each new item is taken out
139 * and the larger items slide one place right until its spot is found.
140 * Very fast on lists that are already almost sorted (our tables usually are).
141 * Time: best O(n) (already sorted), average and worst O(n²)
142 * Space: O(1) extra (plus the copy) · Stable: yes
143 */
144function insertionSort(records, field, order) {
145  const list = arrayCopy(records);                  // sort a copy, so the table keeps its own order
146  const direction = order === 'desc' ? -1 : 1;
147  let comparisons = 0;
148  let shifts = 0;
149  for (let i = 1; i < list.length; i++) {           // 1. items before i are already sorted
150    const current = list[i];                        // 2. take out the next item
151    let j = i - 1;
152    while (j >= 0) {
153      comparisons++;
154      if (compareForOrder(list[j][field], current[field], direction) > 0) {
155        list[j + 1] = list[j];                      // 3. a bigger item slides one place right
156        shifts++;
157        j--;
158      } else {
159        break;                                      //    found the spot
160      }
161    }
162    list[j + 1] = current;                          // 4. drop the item into the gap
163  }
164  recordRun('Insertion sort', comparisons, shifts);
165  return list;
166}
  1. Everything before position i is already sorted; current is the next item to place.
  2. While the item on the left is bigger, it slides one place to the right (a “shift” — counted as a move).
  3. When a smaller-or-equal item is found, the loop stops (that is why a sorted list costs only n−1 comparisons) and current drops into the gap.

Sign-in and “is this e-mail taken?” happen often; a hash table answers in O(1) on average instead of scanning every staff member. The e-mail is lower-cased first, so capital letters don’t matter.

What is a collision and how do you handle it?

Two keys landing in the same bucket. Each bucket is a small array (a chain); we compare the keys in that chain one by one. The table grows (about ×2 buckets, rehashing every key) when there are more than 0.75 keys per bucket, so chains stay short.

Do you store passwords?

No — only a salted hash (the salt is the staff id or the request id). Sign-in hashes what was typed and compares the results. Our hash is a teaching hash; a real system would check passwords on a server with a slow algorithm such as bcrypt.

Likely panel questions

Why does the bill id start with the year and month?

Because the array is sorted by id, all bills of one month sit next to each other. A binary search jumps to the first one and a short scan collects the rest — O(log n + k) instead of reading every bill.

What happens to someone connected on the 31st?

In a month without a 31st the period starts on that month’s last day (e.g. February 28), then goes back to the 31st when it exists. The due date is always 15 days after the period starts.

How do you stop double billing?

The bill id is built from the month and the account, so a second bill for the same month has the same id — findBill (binary search) finds it and the bill is refused.

How do you detect a re-used reference number?

Every payment is stored in a hash table under “METHOD:REFERENCE”. Validation looks that key up once; if a confirmed payment, or an earlier report still waiting, is listed there, check 5 fails. Only the later report is the duplicate — the first one is not blamed, and declined reports don’t count.

Why doesn’t the public form reject a used reference right away?

That would let anyone test other people’s reference numbers. The customer’s form only checks the format; the duplicate check is done by staff.

Why can’t staff confirm a payment when a check fails?

confirmPayment runs the checks again itself and refuses — so a bill can’t be marked paid for a wrong amount, a bill that is already paid, or a fake reference, even by mistake.

Reading Big-O in one minute

What it means

Big-O describes how the work grows when the data grows, ignoring fixed costs. O(log n) grows very slowly (double the data → one more step); O(n) grows in step with the data; O(n²) grows with the square (double the data → four times the work).

Time vs. space

Time counts the steps (comparisons, moves). Space counts the extra memory the function needs besides its input — e.g. a sort that copies the list is O(n) space, a binary search is O(1).

Appendix B

General questions — any member may be asked

Why is the whole website one HTML page?

Our data lives in JavaScript arrays, and arrays exist only while the page is open — they cannot be carried to another HTML file. So every screen is a section of one index.html, and the router shows the section named after the # in the address. The arrays stay alive while you move between screens.

Where is the data saved? What happens when you refresh?

Only in memory (the arrays in backend/database.js). There is no localStorage, cookie or server. Refreshing the page loads the sample data again — this is expected for the project rule, and it also makes every demonstration start from the same state.

Why didn’t you use push, sort, indexOf, filter and the other built-ins?

It was a project rule, and it shows we understand what they do. Each one has our own version in assets/js/dsa/: arrayAppend (push), arrayInsertAt / arrayRemoveAt (splice), linearSearch (indexOf / find), linearSearchAll (filter), insertionSort and others (sort), textFind (includes), trimText, splitText and toLowerText — and no regular expressions.

What does “procedural, not OOP” mean in your code?

There are no classes, no this and no methods. Data is plain records (e.g. a queue is { items, front, count, capacity }) and every operation is a separate function that receives the record: enqueue(queue, item), stackPush(stack, item), hashPut(table, key, value).

Aren’t O(n²) sorts too slow?

Not for our data: the lists have tens to hundreds of records, and the tables are usually already in order, which is insertion sort’s best case — O(n). They are also simple to verify, and insertion and bubble sort are stable. The Benchmark lab on the Algorithms page runs the three sorts on the same random data and shows the exact comparison counts, so the difference can be seen live.

Why keep the arrays sorted instead of sorting when needed?

Records are looked up far more often than they are added. Keeping each array sorted by its key (append when ids only grow, sorted insert otherwise) lets every look-up be a binary search — O(log n) — instead of a linear search, and each month of bills becomes one contiguous block (Module 11).

Why hash tables, when you already have binary search?

Binary search only works on the key the array is sorted by. Staff are sorted by id, but sign-in searches by e-mail; payments are sorted by id, but the duplicate check searches by reference number; wrong sign-in tries are counted per e-mail. A hash table indexes that second key and answers in O(1) on average, without a second sorted copy that would cost O(n) per insert.

How does Undo work?

It is a stack. Every admin action pushes one step holding its operations (insert / update / remove) and the “before” values. Undo pops the newest step and reverses its operations. One step can hold many operations — generating a month of bills, or confirming a payment (payment + bill). Only the last 25 steps are kept, and the stack is cleared at sign-in and sign-out so staff only ever undo their own work. Customers’ actions are not on the stack, so Undo refuses a step that would break one — e.g. deleting a bill a customer already reported a payment for, or re-opening a declined payment after the customer sent a new report. Each toast’s Undo only reverses the action that toast announced.

How secure is it?

It is a class project that runs entirely in the browser, so we are honest about the limits. What we did: passwords are stored only as a salted hash (FNV-1a repeated 400 times — a demo, not a real password hash), five wrong passwords in a row for one e-mail (counted in a hash table) pause sign-in for 30 seconds, the sign-in error never says whether the e-mail or the password was wrong — nor, through the registration messages, which e-mails belong to staff — staff screens need a signed-in account, and everything shown on screen is escaped so typed text can’t run as code. A real deployment would need a server and database, a proper password hash (bcrypt or Argon2) and HTTPS, because anything in the browser can be read with developer tools.

How do you prove the complexities?

Every search and sort records its comparisons and moves; the Algorithms page shows the last runs, the live sizes of every structure and the benchmark. The traces in this reviewer were produced by running our actual functions on the sample data.

Did you use the Date object?

Only to read the clock: readClock reads today’s date from the computer, and Date.now() / performance.now() give timestamps for the sign-in pause, the activity log and the sort stopwatch. All date maths — adding days, next month, days between two dates, leap years — is our own day-number arithmetic in backend/utils.js.

What would you improve with more time?

A real server and database so data survives a refresh; sending e-mail or SMS for application updates and bills; online payment through the payment provider’s API instead of reported references; and a balanced tree or database index once the tables grow to many thousands of records.
